# Partial offline tender recovery

The offline payment dialog assigns the checkout UUID before showing payment entry. Each counted cash payment or operator-verified manual payment is saved under that order and its zero-based payment index before the dialog displays it as saved. Ordinary online payment dialogs retain their existing checkout behavior.

The operation journal stores an immutable `offline_payment_fragment` at UUID v5(checkout UUID, `tender:<index>`). Its payload includes the original cart/product observations, grant, device, shift, currency, tax/settings revision, expected order total, exact cash received or manual reference/confirmation, and the operator observation time. This is confirmed physical/manual tender evidence, not a receipt or payment-provider authorization.

Evidence is written before a key, expiry or signing recheck. If authorization disappears after the operator confirms payment, the fragment survives as a review record. An authorized device then appends a separate immutable `offline_tender_proof` at UUID v5(checkout UUID, `tender-proof:<index>`), signed over the fragment digest, checkout UUID, grant UUID and index with the `NexaPOS:tender:v1\n` domain. Tender proofs are review evidence; the server accepts only the existing complete, separately signed sale-event protocol.

A retry retains the original index, amount, reference, timestamp and UUID. While a write is uncertain, fields are disabled and the dialog offers **Retry saving original payment**. Saved tender cannot be removed. Closing the dialog or restarting reloads the original cart and saved allocation. A partial allocation can collect only its remaining amount under current valid offline authorization. Expired, revoked, locked, stale catalog, insufficient stock or exhausted grant authority cannot authorize another sale; preserved evidence remains readable/exportable for an authorized reviewer. A storage failure is shown as uncertainty, never as confirmed persistence.

When an allocation is complete, the coordinator checks the exact frozen order and all original fragments. Missing proofs can be recovered under valid original authority without collecting payment again. The existing `offline_payment_intent` and atomic local sale/outbox transaction still complete the receipt. Only after the matching committed local event exists does the journal append one immutable `offline_tender_finalization` seal, binding the checkout UUID, device, document and event digest. On reopening, the seal must match the actual committed event before the order stops blocking new collection. Fragment/proof rows remain append-only; they are never individually removed or confirmed in a sequence that could crash halfway.

Unresolved fragments block a different checkout, replacement grant and normal signed grant release. Retrying an already prepared grant may recover its original authorization without extending its expiry. A signed provisional receipt remains pending synchronization and does not claim backend or provider acceptance. Partial records that cannot become a receipt require explicit review; this change provides no automatic refund, discard, replacement sale or grant-barrier waiver.

Validation covers reopening native journal and financial SQLite files, exact replay after expiry, lost write responses, stale cart prices, key removal, expiry preserving unsigned paid evidence, delayed writes, disabled editing/removal during uncertainty, cancellation/restored partial allocation and expired read-only recovery. Hardware interruption and OS secure-vault behavior still require Windows/Android device acceptance.
