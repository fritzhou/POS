# Employee PIN management

Phase 5 supplies online PIN setup, change, reset and supplemental verification. A PIN does not sign in, unlock an offline workspace, create a Supabase session, change a role, or approve a sale, discount, void or refund. Privileged checkout operations continue to require the authenticated account's current server role. Operation-bound manager delegation is still a separate integration gate.

`PinSecuritySection` loads actual account status and server-authorized reset targets. An employee sets a 6–12 digit PIN, or supplies the current PIN when changing one. Repeated identical digits and common increasing/decreasing sequences are refused for new PINs. The fields are obscured, suggestions/autofill are disabled, and completed requests clear the text controllers. PIN text stays in memory for the HTTPS request; it is never written to SQLite, the durable operation journal, grants, exports or audit metadata. Dart strings cannot promise immediate zeroization in process memory.

An Owner can reset an active member's PIN. An Admin can reset active Manager, Cashier and Inventory Staff accounts whose complete branch assignment is within the Admin's current scope. A Manager can reset only Cashier and Inventory Staff accounts whose complete branch assignment is within the Manager's scope. A reset needs an explicit reason and stable request UUID. It removes the old hash, increments the PIN revision and clears PIN lockout; the employee subsequently sets a replacement through their own verified online Auth session. The reset never chooses or reveals a replacement PIN. Audit events retain the target's branch and role scope at the time of the operation.

The `employee-pin` Edge function verifies the bearer with Auth `/user`, then requests a bounded authorization capability with that same user's JWT. PostgreSQL records only the required verified claim context and actor, action, request UUID and expected PIN revision. The service-only completion RPC independently checks current verified membership and branch access, current privileged MFA policy, capability lifetime, and the original JWT expiration. A different actor, expired capability, revoked membership or intervening PIN revision cannot complete the operation. SQL and Edge responses project safe status fields; application roles cannot read the private hash, capability or reset-request tables. Stable request retries return the original one-time result rather than changing its meaning.

The server uses `pgcrypto` bcrypt with a fresh random salt and cost 12. Argon2id was the original preferred algorithm; bcrypt is the implemented dependency-free PostgreSQL boundary. A short PIN still has limited entropy: five failed checks lock the member's PIN operations for 15 minutes, with attempts persisted atomically across requests and processes. Returning a denied result rather than throwing preserves the failed-attempt state. Authorization capabilities are limited to ten simultaneous pending requests per member and expire after two minutes. They are not manager approval tokens.

Deploy migrations 008 and 009 before deploying `employee-pin`. Configure `PIN_ALLOWED_ORIGINS` for web clients and the usual Supabase URL, publishable/anonymous key and service-role secret in the server environment. The service key never belongs in Flutter defines. Keep provider request-body/SQL-parameter logging disabled for PIN inputs; the application function itself neither logs nor returns supplied PINs or raw provider errors. Recovery-only AMR claims and the client recovery-session guard reject PIN mutation.

Validation uses an isolated PostgreSQL service, HTTP gateway fixtures and Flutter widget fixtures. It does not establish live project deployment, physical secure-vault behavior, manager checkout delegation or offline PIN identity.
