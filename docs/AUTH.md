# Authentication foundation

The presentation depends on `AuthRepository`. `SupabaseAuthRepository` calls Supabase Auth and the deployed PostgreSQL membership/RPC boundary. `NotConfiguredAuthRepository` cannot produce an identity, membership, or offline session. The disconnected design preview callback has no authenticated context.

Configure the public project URL/client key at runtime. Initialize Supabase with `FlutterAuthClientOptions(localStorage: storage, pkceAsyncStorage: storage, authFlowType: AuthFlowType.pkce, autoRefreshToken: true)`, where `storage` is one project-scoped `SecureSessionStorage` shared with the repository. Neither an Auth token nor a password belongs in Drift or ordinary preferences. Supabase's own refresh lifecycle handles live sessions.

`Remember this device` defaults off. Without consent, refresh sessions and PKCE verifiers remain in memory. Removing consent deletes previous persisted secrets; sign-out clears the session/verifier/consent keys. With consent, `flutter_secure_storage` stores them through its platform adapter. Tests verify the policy using an injected secret store; host tests do not establish Windows/Android vault behavior. Browser previews are development feedback and do not claim an OS-backed browser keystore.

Email sign-in is implemented. Employee ID resolution is **Coming Soon** and cannot trigger anonymous employee-email lookup. Employees see **Need access? Contact your administrator.** Public employee account creation is absent.

The separate new-business form collects business name, full name, email and a confirmed password. Signup stores only non-secret setup intent in Auth user metadata; metadata carries no authority. Supabase email verification must complete before the signed-in owner can finish setup through `bootstrap_organization(p_business_name,p_full_name)`. The server derives identity and role, checks verified email, and creates a new business transactionally. No client-provided user ID or role is sent. Existing accounts get a safe sign-in/recovery route. Multiple active businesses require an explicit business choice rather than selecting a more privileged membership automatically.

The live app opens only after successful server queries return an active membership with authorized active branches. Server-rejected, missing, disabled, empty-branch and unavailable membership results fail closed. The server continues enforcing permissions through RLS/RPC; UI checks are presentation checks. Later authoritative idle/session/device and offline-grant enforcement remains separate work.

Forgot-password success always displays exactly:

> If an account exists for this email, recovery instructions have been sent.

Account-specific recovery errors never expose identity existence. Service failures display a sanitized availability message. Recovery requires a configured allowlisted redirect URL; merely setting one is not evidence of email delivery or callback handling.

The reset form is activated by Supabase's `AuthChangeEvent.passwordRecovery` and a live validated session. An ordinary sign-in, route string or query switch cannot activate it. A recovery session remains restricted to its verified identity through transient Auth stream failures and token refresh; those events cannot convert it into business access. It updates the password through Supabase and requests local sign-out. Password-update success does not claim global revocation, MFA, a security notification, or a client-written audit event.

Supabase Dashboard prerequisites: enable email/password Auth and email verification; configure delivery/rate limits; allow only intended verification/recovery redirects; deploy schema/RLS/bootstrap migrations. Android App Links and Windows URI/HTTPS registration and end-to-end verification/recovery callbacks require real target platform tests. A persisted Auth session alone never provides offline business authorization. Phase 4 additionally requires the same remembered verified identity, pinned signed grant, complete cache, enrolled secure key, scope and clock checks in a separate explicit workspace. Fresh membership denial/recovery/logout blocks that path; no new offline password/PIN sign-in is implemented.

Phase 2 adds an optional `InvitationInbox` to `AuthGate`. `SupabaseInvitationInbox` calls authenticated `list_pending_invitations()` and `accept_employee_invitation(p_invitation_id)` RPCs. Invitations display server-assigned business, role and branches as read-only details. A successful acceptance reloads actual memberships before the shell opens. Existing memberships remain usable while an invitation is pending or the inbox is unavailable; users can view, defer and return to their original business. Two businesses require explicit selection after acceptance.

The recipient must be signed in with a verified matching email. New/passwordless accounts use `requires_password` from the server to create and confirm an account password through Supabase Auth before acceptance. Existing users with a password keep it. The server independently checks `auth.users.encrypted_password` presence, verified recipient email, invitation state/expiry, inviter authority and branch validity. No password is sent to PostgreSQL, no client-selected role or branches are submitted, and no recovery-only session can accept invitations through the app.

The Phase 2 invitation protocol intentionally uses Supabase Auth's signed invitation/email OTP action to establish proof of the recipient's email. Once Auth validates that action, the authenticated verified email may list and explicitly accept the matching server invitation. There is no separate custom organization invitation secret entered into Flutter. Consequently an already authenticated account with the same verified email can also accept its invitation. Expiry/revocation/single acceptance and current inviter authority are still enforced by the server invitation record. Live email delivery and platform callbacks must be tested with a configured project before connection is claimed.

Phase 5 implements TOTP enrollment and server privileged MFA policy, idle locking with fresh online same-account unlock, and explicit provider refresh-session revocation. Phase 4 signed enrollment/grants remain the separate offline boundary. Deferred: Employee ID resolver, cashier-to-manager financial delegation, authoritative password-change notifications, general Auth session/device binding and physical callback/vault certification. Phase 3 privileged discounts/refunds/voids use the operator's own verified online membership; a cashier cannot supply a client-side manager identity as approval. No live project credentials are supplied, so real invitation/verification/recovery email delivery, token refresh against a live server, and production lockout settings remain **Not Yet Connected** until exercised.
