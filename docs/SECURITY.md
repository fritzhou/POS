# Security boundaries in Phases 1–6D

Phase 1 implements identity/session and local-durability foundations. Phase 2 adds online catalog, directories, employee access, invitation, business-settings and audit source. Phase 3 adds authenticated online checkout, shift and branch-inventory transactions, immutable sales/receipt snapshots, and compensating refund/void documents. The SQL/adapter tests validate individual boundaries; they do not establish a deployed Supabase project or live Auth/email/callback behavior. Phase 4 adds signed device enrollment/grants, explicit offline checkout and financial ingestion. Phase 5 adds encrypted local files, device/PIN administration, MFA policy and idle locking; live deployment and physical platform enforcement remain unvalidated. Card/e-wallet evidence remains manual; no provider authorization, capture or refund API is connected.

Phase 6A extends these boundaries to immutable purchase orders/receipts, recorded external/own-drawer expenses and full compensation, and server-posted reports. Current identity, membership, branch and configured privileged MFA are checked before every new operation and accepted-request replay. Purchase costs and historical currencies do not change with the catalog. Drawer effects derive only from immutable confirmed expense/return documents; a new reversal cannot rewrite a closed drawer. Reports use one consistent server snapshot, keep currencies separate and exclude unposted/review-only offline evidence. Cashier reports require an explicitly selected own shift and expose no purchase, expense or cost side fields.

## Identity and secret storage

Identity and business authorization are separate. A Supabase session alone cannot enter the application shell: the app must load a current, active membership and authorized branch. A transport failure can offer a separate grant-backed device workspace, after the same remembered identity, pinned signature, scope, complete cache, secure key and time checks pass. It never sends a cached membership into the normal online shell. Definite authorization denial invalidates offline keys. Read-only **DESIGN PREVIEW** has no session, permissions or business data.

Passwords exist only in short-lived form/controller memory. Tokens and PKCE verifiers use OS-backed storage only after explicit remembered-device consent. Without that consent, the current session remains memory-only. Serialized storage writes prevent an older queued persistence operation from recreating secrets after logout or consent removal. Logout clears session secrets and presentation state. Drift never stores passwords, PINs or tokens. Phase 5 native factories separately encrypt business/journal files with SQLCipher. Windows/Android vault and physical file/key recovery still require platform validation.

Public project URL/publishable or anon keys are build configuration. Service-role/secret keys are rejected before Supabase initialization. SMTP and email/payment credentials belong only in backend secret settings. Errors/logs must exclude raw backend responses, tokens, recovery URLs, passwords and PINs.

## Tenant, branch and management authorization

RLS reads current memberships, enforces organization and applicable branch scope, and rejects disabled members. UI menu filtering is presentation only. Organization-shared catalog records differ from branch stock: there is no live stock quantity merely because a product exists. Phase 2 suppliers/customers may be shared or explicitly branch-scoped; branch staff cannot write shared directory records or records from an unauthorized branch. Product cost is omitted from direct client column grants and masked for Cashiers by the list RPC.

Normal clients cannot mutate memberships/assignments, invitations, catalog/directories or business settings directly. Privileged `SECURITY DEFINER` RPCs use fixed empty search paths, fully qualified objects, narrow explicit execution grants, verified identity and current membership checks. Writes reject unsupported fields, require an audit reason and validate expected revisions; stale revisions produce a conflict instead of overwriting someone else's change. Same-organization foreign keys prevent cross-tenant category/supplier/branch references.

Owner bootstrap derives identity from Auth, requires a verified email and creates organization/Main Branch/Owner membership atomically. Concurrency and retries do not duplicate ownership. Employee access changes cannot affect the acting user's own access or Owner. Admin cannot edit another Admin, grant Admin or delegate all-branch access. These checks are server-enforced; employees never self-select a role. Membership disable affects access to that organization, not the person's global Auth account or another business.

## Employee invitation identity and delivery boundary

Flutter sends invite requests to the `employee-invitations` function with a user bearer JWT. The function verifies it against Supabase Auth `/user` and prepares the invitation RPC with that same actor JWT. It never substitutes its administrative credential for the actor's preparation check. SQL derives the inviter and checks current role, every requested branch, employee ID conflict and the request's canonical payload. A stable request UUID deduplicates retries; reusing that UUID with different fields fails.

Delivery claim/finish RPCs are service-only. Claiming locks the invitation and rechecks current inviter authority. A new identity uses Supabase's server-only Auth invitation API. Only an authoritative `email_exists` response permits the existing-account Auth email-link fallback with `create_user: false`. HTTP failures, malformed errors and timeouts do not authorize that fallback. Auth success means the provider accepted the request, not proven inbox delivery. Uncertain outcomes remain `sending` and are not automatically redispatched. Definitive rejection becomes `failed`; no failed/uncertain response is presented as completed email delivery. The matching server claim is required to record a delivery outcome.

Supabase Auth owns its expiring, single-use email action credentials and validates them before issuing a signed authenticated session. **NexaPOS has no separate clear organization token or invitation-token digest.** An invitation UUID identifies a business record and does not authenticate or authorize acceptance. Action URLs are not returned to Flutter or recorded in application logs. Redirects are server-configured and must also be in the Auth redirect allowlist. Browser CORS origins are explicitly allowlisted; native requests still require a valid JWT. The handler bounds content type, body size and fields.

The recipient inbox uses a verified Auth session. SQL derives the confirmed recipient email from `auth.users`, returns only that identity's `sent`, unused, unexpired, unrevoked invitations, and rechecks the inviter's current authority. A verified recipient can discover the invitation after regular sign-in without possession of a second application token. A new passwordless identity must establish an Auth password before acceptance; password verifiers remain inside Auth and are never returned by the inbox RPC.

Acceptance sends only the invitation ID. SQL locks/rechecks the recipient, email, password presence, role/branch authority, pending/delivery state and expiry; creates membership from the stored role/branches; consumes the record; and records audit in one transaction. The client cannot supply its own role, recipient or branch scope. Duplicate/replayed acceptance fails safely. The app also blocks invitations during recovery-only state and rechecks identity after asynchronous password update, so a late result cannot apply to a switched account.

Phase 6D implements the administrator history/detail, original email-request retry and durable revocation UI. History and immutable action replay require current verified Owner/Admin authority, configured privileged MFA and the complete original branch set, including inactive branches. Admin invitations can be mutated only by an Owner. Original retry fields are exposed only to their eligible creator; retries retain the same request UUID and exact canonical payload. Unknown `sending` has no automatic reclaim or guessed reconciliation. Production must additionally validate actual new/existing-account Auth email behavior, delivery quotas and platform callbacks in a real project.

Revocation locks the invitation against acceptance and dispatch changes and commits its immutable action/request receipt and audit atomically. The native encrypted journal retains intent and attempt counts before RPC dispatch. Foreign/malformed success or later denial after an uncertain attempt cannot clear the pending original operation. Every lifecycle update advances revision; a stale new action fails rather than changing newer history. Revocation does not disable an accepted membership or recall an already claimed email. Legacy accepted/prepared delivery history remains readable without invented provider evidence. See [PHASE6D_CONTRACT.md](PHASE6D_CONTRACT.md).

New invitation preparation uses an organization advisory lock and rolling limits of 20 per ten minutes and 200 per 24 hours. Known idempotent status requests return before the new-operation cap. Definitively rejected dispatch has a ten-second cooldown; `sending` is never automatically reclaimed. The function maps dedicated SQLSTATE `NX001`/`NX002` to HTTP 429. Supabase's own email rate limits remain independently required.

## Audit and financial immutability

PostgreSQL audit and reserved financial records are immutable to normal writers. Management audit identifies the actor from the verified session; delivery receipts identify system-side actions. UI clients cannot forge an audit author, write arbitrary audit success, or edit/delete history. A trusted database superuser and the deliberately restricted backend service role remain administrative boundaries.

Security audit scope uses the complete event branch snapshot. An employee-access event includes previous and new branches/access; an invitation event includes every invitation branch and its all-branch flag. A scoped Admin must currently cover every event branch and cannot use a null/first branch or a target's later reassignment to inspect a security event outside that scope. Owner/all-branch Admin can inspect organization audit, including historical inactive branches. Legacy security events without complete scope evidence fail closed for scoped Admin. Shared catalog/business audit has an explicit organization-wide scope; this must not become a shortcut for employee/security history.

Operational audit entries require the applicable authorized branch and eligible role. Manager/Inventory Staff visibility must not expand to catalog/global/security history simply because navigation shows an audit route. Cashiers cannot read the audit ledger. Immutable audit does not imply that login/logout/password-security event ingestion is connected; those authoritative Auth-event integrations remain deferred.

Local financial snapshots and the outbox are atomic, scoped, append-only and tested for restart/replay/crash recovery. Legacy local records do not constitute offline permission or server acceptance. Phase 4 authorized sales add immutable device signatures and detached grant/tender evidence, while authenticated ingestion derives the actor and validates exact replay, frozen financial math and current membership/device authority. Accepted links are separate append-only records. Source-backed deficits require explicit reconciliation. No local signature proves provider payment success. Phase 3 online request receipts are a separate protocol and must never be used to manufacture an outbox acknowledgment.

## Online financial authority and retry safety

The Phase 3 server derives the actor from verified Auth identity and locks/rechecks the active membership, role and assigned active branch. Caller-supplied user IDs, role labels, product prices, totals, stock counts and client device names are not authority. Cashiers can inspect only their own accepted sales/shifts in their authorized branch. Supervisory actions require the current Owner/Admin/Manager actor and applicable branch; entering a Cashier-side PIN does not supply that identity. Manager amount ceilings and delegated approval tokens remain deferred.

Only the narrow financial RPCs can accept a sale, close a shift through an appended closure, receive/adjust stock or append compensation. Ordinary clients have no direct financial-history mutation grant. Request UUIDs are scoped to organization and actor. Canonical JSONB request content is stored privately and serialized for duplicate/concurrent requests. Every retry first rechecks current authorization, then returns the same accepted document identity for identical content; changing the payload under that UUID is rejected. Associated current projections, such as later compensation totals or shift cash, may change while the accepted document remains immutable. Idempotency does not permit a disabled employee to recover privileged business data.

The native pending-operation journal persists the frozen request before submission so a lost response or restart can retry the same operation. A timeout remains an unknown outcome. Retry must retain actor, organization, branch, request ID and content; switching branch or session cannot repurpose pending requests. A pending record is not evidence that the server accepted anything. A later authorization rejection after an unknown attempt also cannot prove that the earlier transaction failed; preserve it for authorized reconciliation. Confirmed receipts are parsed and checked against the expected request/branch before success is presented. Phase 5 native journals use SQLCipher with independent OS-vault keys; migration and platform backup/key recovery are documented in LOCAL_SECURITY.md.

Checkout validates active products, expected catalog/settings revisions, customer scope, currency, quantities, discount authority and payment evidence. Exact minor-unit arithmetic is capped to interoperable integers. Supported transaction currencies are PHP/USD/EUR/GBP/AUD/CAD/SGD with two-decimal precision; unsupported codes fail closed. Whole-unit quantities are enforced. Prices/settings/cost evidence are snapshotted so later catalog or business edits cannot rewrite receipt history; Cashier-visible receipts must exclude product/receiving cost evidence.

Sale header, immutable lines/payment evidence, unique receipt identity, stock movements, request result and audit commit in one PostgreSQL transaction. Product/balance locks follow a stable order; ledger enforcement rejects a negative branch balance and rolls back the complete transaction. The balance is a projection of the movement ledger, not a mutable catalog quantity. Receiving cost evidence does not silently change catalog cost.

Refund/void actions append compensation against the original sale and payment. Cumulative quantity and money bounds prevent repeated or concurrent over-refund; stable cumulative allocation preserves exact final totals. A void requires an untouched full sale. The privileged acting user needs a current open shift and a reason; compensation cash affects that shift's expected cash. The original sale, line snapshots and receipt remain unchanged. Explicit `return_stock` defaults false and only a confirmed physical return restores selected units to the original branch. Manual noncash compensation records operator evidence; actual external refunds require separate operator/provider action.

One open shift per organization/actor is allowed across branches. Cashiers close only their own shift; an authorized Owner/Admin/Manager may close a shift in an assigned branch. Shift currency is immutable. Closing cash variance comes from counted cash versus server-derived opening cash plus applied cash sales minus cash compensation in that shift; recorded Card/GCash/Maya/Other evidence does not become cash. Closing and sale acceptance are serialized so a concurrent checkout cannot silently commit into a closed shift. Business currency changes do not rewrite open shifts or historical money and may require closing/reopening before new transactions. Cash-in/out event workflows are not implemented.

## Recovery and deferred production security

Password recovery uses the neutral account-existence message. Only a Supabase recovery session enables the app's password-update route; refresh failures retain the recovery restriction for that same identity. Production recovery also needs verified platform/HTTPS callbacks and allowlisted redirects. Do not claim password-reset audit ingestion or global session revocation from a successful client response alone.

Phase 5 implements server-only rate-limited PIN change/reset, real TOTP setup and Owner/Admin AAL2 policy, enrolled-device management and audited lost-key review, source-backed notices, and whole-Navigator idle/background locking. No PIN result supplies an identity or financial delegation. Authoritative Auth login/logout/failed-login/password security-event ingestion still requires a provider event pipeline. Supabase project login protections and live JWT behavior must be tested with the actual project.

Offline business authorization requires a server-issued, device-bound, expiring grant and a tested key/lockout lifecycle. Network loss must not bypass identity, recovery, membership or device checks. Immediate revocation on a disconnected device is impossible; grants bound that exposure to at most eight hours and constrained sales/value. SQL rechecks current authority even on replay. OS-stored software Ed25519 keys and clock checkpoints are not hardware attestation or a tamper-proof clock. Offline discounts/refunds, manager delegation, shift opening/closing and security changes remain online-only.

Before production, exercise live JWT/Auth/PostgREST behavior, employee disable with still-valid tokens, invitation replay and concurrency, branch-scope audit isolation, server-side invitation abuse limits, callback replay/expiry, native secure storage, local-data encryption, backup restoration and signed release/platform handling. Current local tests and the debug APK do not close those gates.

## Phase 5 enforcement and limits

[PHASE5_CONTRACT.md](PHASE5_CONTRACT.md), [SECURITY_BACKEND.md](SECURITY_BACKEND.md), [SECURITY_UI.md](SECURITY_UI.md), [MFA.md](MFA.md), [PIN_SECURITY.md](PIN_SECURITY.md) and [LOCAL_SECURITY.md](LOCAL_SECURITY.md) document exact contracts. Idle locking preserves payment dialogs/keys; password unlock uses an isolated provider session and verifies fresh unchanged membership. Logout has a separate key-removal lifecycle. Global sign-out verifies refresh-session revocation before clearing the shared session, without claiming immediate access-token revocation. Android excludes application backup/transfer and secures screenshots/recents; physical OS behavior remains untested.

Privileged service paths use short verified-user-context capabilities when MFA is enabled; supplied actor/AAL labels are never authority. Original paid ingest remains reachable for review with current same-actor membership. Enrolled-device revocation does not imply every online Auth session is device-bound. Financial manager delegation, Auth event notifications, recovery escrow, hardware integrations and production signing remain acceptance/integration work.

Phase 6B adds branch maintenance and physical stock logistics through migrations 013/014. Read [PHASE6B_CONTRACT.md](PHASE6B_CONTRACT.md). Current authorization and privileged MFA precede every replay; dispatch requires both endpoints, receipt requires its destination and transit return its source. Supplier returns reference original purchase receipt quantities and costs and do not pay suppliers. Branch deactivation blocks retained grants, unresolved stock/transit, open shifts and outstanding orders. Codes remain immutable, referenced product units cannot change, and scope changes reload server membership. Preserve encrypted logistics intents, original evidence and UUIDs through uncertain responses. Direct service branch/catalog writes are revoked; use validated RPCs.

Phase 6C receipt output and keyboard input are described in [PHASE6C_CONTRACT.md](PHASE6C_CONTRACT.md). Verify bundled fonts with `python3 tool/verify_receipt_fonts.py`; setup performs this before frozen dependency resolution. PDF rendering has no runtime font download. Print/PDF actions preserve original records and recheck source, auth and lock generations before native handoff; output is an explicit plaintext customer copy managed by the OS, separate from encrypted business databases and reviewer proof. No physical completion or provider delivery is implied. Keyboard scanner capture starts disabled and pauses for forms, dialogs, locks and unavailable capture authority.
