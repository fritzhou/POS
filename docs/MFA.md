# Authenticator verification

Phase 5 adds Supabase Auth TOTP enrollment, challenges, verification and removal. These operations use the installed Supabase Dart SDK and the configured project's Auth service. No sample factor or code grants access in the application.

`SecurityMfaPage` lets a signed-in account name an authenticator, obtain its live setup key, enter a six-digit time-based code, verify an existing factor, and remove a verified factor after the current session reaches AAL2. Setup uses manual key entry in an authenticator app. The key is hidden initially, shown only on deliberate reveal, and retained only by the open setup form. It is never written to Drift, the operation journal, logs, notifications, or clipboard. The code field is cleared before dispatch. Every verification attempt obtains a new server challenge; expired and invalid challenges remain blocked.

Closing or canceling an enrollment attempts to remove its unverified factor when the same account is still signed in. If connectivity or an account change prevents cleanup, the factor remains unverified in Supabase Auth and never establishes AAL2. After reconnecting, the account can cancel unfinished setup explicitly. A verified factor cannot be removed through the enrollment cancellation path.

The adapter performs MFA operations in an isolated in-memory GoTrue client with token refresh and local persistence disabled. Factor discovery reads the authenticated `/user` endpoint instead of calling the SDK's factor-list helper, which refreshes tokens. Successful verification imports the returned session into the shared client only after the original actor/generation/recovery checks and a genuine AAL2 result. The public synchronous `setInitialSession` API emits an Auth event so existing secure session persistence and fresh membership checks receive the upgrade. A delayed response after logout or an account switch cannot restore the old actor's shared session.

`MembershipMfaGate` loads the current business security policy before constructing the authenticated shell. A policy requiring privileged MFA applies to owners and administrators. Those roles must have a freshly discovered AAL2 session before business UI is rendered; an AAL1 account receives the verification/enrollment page. Policy discovery itself is exempt from AAL2 so a newly signed-in account can discover the requirement. Policy and assurance errors fail closed with reconnect/retry and sign-out actions. Policy changes and Auth refresh events cause a new gate check. Business RPCs independently enforce the same policy on the server; the widget is not the authorization boundary.

Enable privileged MFA only after the acting owner or administrator has verified an authenticator. SQL requires current AAL2 for enabling the policy and for policy changes when the requirement is already active. Authenticator management remains available to ordinary signed-in accounts without requiring an organization policy to be enabled first. Recovery sessions do not gain MFA management or normal business access.

The 36 focused MFA tests include 13 tests of the actual installed SDK through an injected HTTP boundary, 15 form tests, and 8 policy-gate tests. They cover factor discovery, challenge expiry, actual AAL2 session import, late responses after logout/account changes, factor removal, secret cleanup, retry behavior and a 320-pixel form. Synthetic test sessions and transport responses are test fixtures, not live provider validation.

Before production acceptance, enable and validate TOTP in the actual Supabase Auth project; exercise enrollment, challenge verification, remembered session refresh, policy changes, account recovery, factor loss and device transitions with real accounts on Android and Windows. Account recovery after losing every factor must use the project's authenticated support/provider recovery process. No PIN, cached grant, role selector or client setting bypasses AAL2. Live provider testing and physical platform secure-storage acceptance are not established by the cloud tests.
