# Phase 5 security backend

Apply the migrations in their filename order. `202610110008_security_management.sql` extends the Phase 4 device/grant service boundary and current membership helpers; `202610110009_pin_security.sql` depends on its security policy and verified assurance helpers. Deploy the updated `offline-sync` and new `employee-pin` Edge functions with these migrations. The old offline gateway cannot satisfy an enabled privileged MFA policy because it does not obtain actual user-context authorization before using its service bearer.

The security inventory is the enrolled offline signing-device inventory. Enrollment proofs, branch bindings, original public keys, revocations and device label history are immutable. The device `last_sync_at` comes from actual retained offline outcomes. This does not claim a list of every Supabase Auth session, its last login, or revocation of online Auth sessions. An offline device revocation prevents enrollment, current catalog pulls, ordinary final releases and new grants on every binding of that device. Existing signed grants on a disconnected device remain bounded by their original expiry; the server cannot notify a disconnected process immediately.

All security RPCs independently require a currently verified Auth user, active membership and current branch access. Owner/Admin device mutations also enforce role hierarchy and every affected binding: a scoped Admin cannot rename or globally revoke an Owner/Admin device or a device assigned outside their branch scope. Current authority is checked before returning an idempotent result. Stable mutation UUIDs bind the actor, organization, action and complete original payload; changed reuse fails with `23505`. Policies additionally use expected revisions, and grant risk review uses the displayed sequence, outcome count and total. Stale review or policy writes fail with `40001`.

The authenticated read RPCs are `get_security_policy`, `list_security_devices`, `list_security_grants`, `list_security_notifications` and `mark_security_notification_read`. Lists take organization, branch, offset 0–100,000 and limit 1–100. Ordinary employees read their own device/grant records and targeted notifications; Owner/Admin views retain their current scope. Notifications inherit the original audit visibility rules for administrators. Actual RPC projection bytes are retained in `test/fixtures/security_sql_contract.json` and the missing-sequence case in `test/fixtures/security_sql_gap_contract.json`; their provenance explicitly identifies isolated mock-Auth test records.

The mutation RPCs are `update_security_device`, `revoke_security_device`, `review_offline_grant` and `update_security_policy`. Each requires a stable request UUID and a trimmed reason of 3–1,000 characters. Device names are 1–120 characters. Security policies default to revision 1, a five-minute idle lock and optional privileged MFA; updates permit idle periods of 1–60 minutes. The app's idle lock is an access barrier requiring fresh online reauthentication, not a claim that an unattended online Auth session was revoked at Supabase.

When a policy requires privileged MFA, current Owner/Admin operations through `require_active_member` require the provider-verified JWT subject to match the actor and `aal` to equal `aal2`. Enabling the policy itself requires AAL2; disabling an enabled policy also requires AAL2. Minimal policy discovery and Auth membership discovery remain accessible to AAL1 so the account can reach enrollment and step-up. This does not trust a locally selected role or a client-reported MFA checkbox. Manager/Cashier identities are outside this Owner/Admin policy gate. Bootstrap remains the initial verified-owner flow.

Restrictive RLS policies also enforce that assurance requirement on direct authenticated table reads and writes for catalog, financial, stock, contacts, invitations and audit records. These policies intersect the original tenant/branch/role rules and grant no additional access. AAL1 Owner/Admin sessions can discover organization and authorized branch metadata, their own membership and branch assignments, their own Auth profile and their own PIN status so they can reach enrollment and step-up. Organization/branch metadata includes the existing branding, currency and location/contact fields; this is an explicit discovery exemption. Other employee membership, assignment and profile rows remain gated. Cashier/Manager access retains its existing row/cost/branch permissions because this policy applies to Owner/Admin assurance. Trusted Edge service access remains a separate Auth-verified boundary rather than depending on client RLS.

Service-role JWTs are not an employee's MFA proof. Before offline enrollment, preparation/finalization, catalog pull or ordinary release, the Edge gateway calls `authorize_offline_operation` with the actual user bearer. Its action is `enroll`, `prepare`, `pull` or `release`; actor identity comes from `auth.uid()`. SQL retains only the verified subject, assurance level and session identifier in a two-minute authorization record bound to the actor, organization, branch, device and action. The service RPC wrappers recheck current policy and current actor scope against that record. An authorization for enrollment cannot authorize a pull; expired authorization fails closed. This is a short user-context authorization bridge, not an Auth session registry. The Edge function still verifies the current bearer on every request.

The PIN service uses a separate short action/request/revision-bound capability created under the actual authenticated bearer. SQL independently rechecks current identity and assurance before completion. PIN hashes use server bcrypt; neither PINs nor hashes are returned in security inventories, stored in local journals, or included in audit/notification metadata. PIN configuration, changes, resets and the server-triggered lockout emit source-backed notifications. Successful verification produces an audit rather than notification noise. These PIN APIs do not yet authorize manager checkout overrides or refunds.

Revocation does not erase money already captured. Grant-specific verification context can return the retained public key and original signed grant under the same current authorized actor. Exact accepted/reviewed replay returns its immutable original result. A new original event observed before revocation and within its signed capture lifetime is validated with the original prices, tax, tender, digest and signature, then retained as `DEVICE_REVOKED` review instead of posting a sale or stock movement. Ordinary ingestion retains its 72-hour grace. New capture observed at or after revocation is denied. The app retains failed original records for inspection/export.

A missing signing key cannot produce an ordinary release signature. `review_offline_grant` instead requires an already revoked device, an expired signed grant, current Owner/Admin authority, a reason, acknowledgement of unknown paid events, and the unchanged displayed known-outcome snapshot. It appends an administrative resolution with all known event identities/statuses/totals and the remaining signed event/financial ceilings. It never inserts a fabricated `offline_grant_releases` row, edits old events, changes historical shift totals, or clears unknown exposure. Only that explicit resolution removes this grant's original shift barrier. Other unresolved grants still block closure. The maximum unobserved exposure is visible before the decision and remains visible afterward.

After administrative resolution, original bounded paid evidence can still arrive beyond the ordinary ingestion grace and becomes `GRANT_ADMINISTRATIVELY_RESOLVED` review. A recovered paid sequence 2 can be retained while sequence 1 is missing; it never fabricates that missing event. The highest observed sequence and actual outcome count remain separate, and remaining event exposure subtracts actual outcomes rather than the highest sequence. A missing earlier original proof can later fill the gap, with uniqueness enforced for event identity and grant sequence. Ordinary unresolved grants retain contiguous ingestion and an ordinary signed release retains its exact final boundary. The event and original proof remain immutable, the original administrative snapshot remains unchanged, and the current remaining exposure decreases as actual outcomes arrive. Reviewed late evidence does not post a receipt into the closed shift, rewrite its closure cash, or deplete stock. Reconciliation cases remain open records; no automatic settlement or compensating payment is invented.

Audit-derived notifications are in-app records, not a claim that email, SMS or push delivery happened. They cover actual device changes/revocations, security policy changes, administrative grant decisions, retained paid-event review, and PIN credential/lockout events. Each points to an immutable server audit source. Read receipts are per authenticated user and append-only. Application roles cannot directly insert notifications, write policies, inspect private risk tables, rewrite history, or manufacture service authorization context.

Validation uses the pinned PostgreSQL image in a network-isolated disposable test container. `test/sql/run.sh` refuses arbitrary containers, images, mounted user storage or published ports before resetting only `nexapos_security_test`. The Phase 5 assertions cover current authority, role hierarchy, idempotency, exact financial exposure, actual closure barriers, late immutable money, assurance/subject/action/expiry checks, and notification visibility. Independent connections also race duplicate policy UUIDs, changed device operations sharing a UUID, and administrator review against an original paid-event uploader. These are mock-Auth SQL boundary tests; live Supabase Auth, provider MFA/session lifecycle and physical secure storage remain separate deployment acceptance checks.
