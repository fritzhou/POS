# Phase 2 data boundaries

The domain interfaces live alongside catalog, people and administration features. Their Supabase implementations require an injected client and the verified, selected `AuthenticatedUser`. A missing backend is represented by presentation's disconnected state rather than by a repository that invents live records. Each operation verifies that the current session belongs to the selected actor, that their email is verified, and that they have branch assignments, both before the request and after its response. The app supplies the recovery-session callback so password recovery cannot enter these features. Responses received after sign-out or recovery begins are discarded; an already submitted mutation may have committed and must be reconciled after signing in again.

The client sends an explicit organization identifier and bounded page to every list operation. PostgreSQL RLS and security-definer operations independently recheck current membership, assigned branches, roles and record scope. Client role fields do not authorize SQL. Product/category catalog records are organization-wide; Phase 3's separate [checkout](CHECKOUT.md) and [inventory](INVENTORY.md) repositories manage branch stock quantities and ledger events. Supplier/customer contacts may be global for an authorized administrator or scoped to an assigned branch for branch staff. Supplier/customer search filters the name and treats `%` and `_` as literal characters.

All edits and deactivations call server-side compare-and-set operations with the displayed revision. SQLSTATE `40001` becomes a public conflict requiring a reload. Creates leave the identifier and revision to the database. Contact edits, employee access, business settings, categories and products follow the same rule. No mutation supplies actor identity, membership role, organization changes, revision changes, stock balances or audit history directly.

`Money.parseMinor` parses decimal strings through `BigInt`, preserves exact PHP cent amounts and rejects negative values, excess decimal precision, exponent notation and overflow. Values are capped at JavaScript's maximum exact integer (`9007199254740991` minor units) so supported platforms retain the same amounts. Reorder quantities preserve a validated decimal string with up to four fractional places, including through server JSON serialization; numeric JSON responses are rejected instead of silently rounding. Tax is an integer number of basis points. Cashier catalog responses expose `costMinor == null` rather than a fabricated cost.

Image and logo references are optional organization UUID prefixes followed by Storage-relative path segments. The validator rejects other organizations, schemes, queries, empty segments and traversal segments. Saving a reference does not upload, fetch or hydrate it. `uploadProductImage` explicitly reports **Not Yet Connected** and performs no network operation.

Employee invitations use the authenticated `employee-invitations` Edge Function and a caller-generated UUID retained across retries. A `200/sent` response means Auth accepted the email request and the server saved its receipt; it does not prove inbox arrival. `202/sending` means the submission outcome remains unresolved. A failed or malformed response never becomes a sent acknowledgement. HTTP `429` reports that invitation requests are rate limited and instructs the user to wait before retrying the same request; the client neither invents a delivery result nor schedules an automatic retry. Email/provider errors and raw PostgREST details are sanitized. Invitation acceptance and the inbox belong to the separate authentication boundary, which can operate before a first membership exists.

Verification: `flutter test test/repositories --no-pub` exercises actual Supabase adapters with an injected HTTP transport, including tenant/branch filters, bounded ranges, CAS conflicts, auth/recovery gates, hidden cashier costs, normalized errors, exact money and invitation delivery states. `flutter analyze` checks these domain/data files and tests. These transport tests do not claim a deployed Supabase connection or real email delivery; SQL security assertions cover server authorization separately.
